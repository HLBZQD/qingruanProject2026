## 结论与分析

### 性能表现总结

#### S1：登录接口

- **TPS 趋势**: 50VU=18 → 100VU=22 → 200VU=27
- **响应时间趋势**: 50VU=2554 ms → 100VU=3889 ms → 200VU=6527 ms

#### S2：公开读接口

- **TPS 趋势**: 50VU=14913 → 100VU=14495 → 200VU=14144
- **响应时间趋势**: 50VU=3 ms → 100VU=6 ms → 200VU=12 ms

#### S3：认证读接口

- **TPS 趋势**: 50VU=22 → 100VU=22 → 200VU=8
- **响应时间趋势**: 50VU=649 ms → 100VU=1359 ms → 200VU=9635 ms

### 综合评价

#### 1. 公开读接口（S2）—— 性能优秀

公开读接口在全部并发级别下均表现优秀：
- **零错误率**：50/100/200 VU 下均无任何失败请求
- **极高吞吐量**：TPS 稳定在 14,000+ 级别，200 VU 下仍保持 14,144 TPS
- **极低延迟**：P95 响应时间仅 4-17ms，SQLite 本地读取性能优异
- **优秀扩展性**：并发增加 4 倍（50→200），响应时间仅增长 4 倍（3ms→12ms），接近线性

#### 2. 登录接口（S1）—— CPU 密集型瓶颈

登录接口受 bcrypt 密码哈希（saltRounds=10）制约：
- **50-100 VU 表现良好**：错误率 0-2%，TPS 18-22
- **200 VU 出现瓶颈**：错误率升至 14.69%，P95 响应时间达 13.6 秒
- **根因分析**：bcrypt.hashSync 是 CPU 密集型同步操作，SQLite 单写入锁加剧竞争
- **优化建议**：降 saltRounds 至 8，或使用 bcrypt.compare 的异步版本，迁移至 Kingbase 获得更好的并发写入能力

#### 3. 认证读接口（S3）—— 多步骤串联瓶颈

认证接口为 3 步串联流程（登录→资料→历史），每步依赖前一步：
- **50-100 VU 表现稳定**：0% 错误率，TPS 22，P95 响应时间 1-1.8s
- **200 VU 严重退化**：错误率 50.42%，TPS 降至 8，P95 响应时间近 30 秒
- **根因分析**：200 并发下 bcrypt 登录步骤成为全局瓶颈，多步骤串联放大延迟
- **优化建议**：引入 JWT 缓存避免重复登录，异步化 bcrypt，使用连接池

#### 4. 总结

| 维度 | 评价 | 说明 |
|------|:---:|------|
| 公开读吞吐 | ⭐⭐⭐⭐⭐ | SQLite 极快，满足 200+ 并发需求 |
| 登录认证 | ⭐⭐⭐ | 50-100 VU 可用，200 VU 需优化 bcrypt |
| 认证流程 | ⭐⭐⭐ | 多步骤串联对高并发敏感 |
| 整体稳定性 | ⭐⭐⭐⭐ | 除 200 VU 极端场景外均稳定 |

**建议**：生产环境使用 KingbaseES 替代 SQLite，配合 Redis 缓存 JWT Token，bcrypt 降级至 8 rounds 或使用异步版本，以满足 200+ 并发需求。
